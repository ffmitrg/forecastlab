# Agent 6改进：防止有用的审查意见被删掉

Agent 6 负责检查前面的分析，比如资料够不够、引用对不对、推演有没有跳步。它写完意见后，程序还会处理一遍，再交给后面的汇总 Agent。
这次改的就是这段处理代码。原来它有时会把有用的质疑删掉，甚至把“不通过”改成“有条件通过”。

## 改动目的
假设今天是 9 月 26 日，我们想预测一个产品会不会在 10 月 1 日发布。如果审查意见是“缺少未来的实际发布结果”，这个要求就不合理：结果还没发生，我们本来就是来预测的。程序可以删掉这种意见。
但“缺少已经公布的 10 月 1 日发布计划”是另一回事。计划今天就可能已经有了，要求补上它是合理的。旧代码可能因为看到未来日期就把这条也删掉，新版会保留。
一句意见里如果还提到“两个来源互相矛盾”，就整条留下；看不准的也先留着。删掉一条不合理意见，不会顺手放过其他问题。只有能确认所有阻断意见都只是索要未来结果时，才会放宽审查状态。
原始意见、每条为什么留或删、状态怎么变，都有记录。导出 JSON 后看 `stage_outputs.review.review_policy_audit` 就能找到，页面暂时没有单独的展示面板。
规则在 `backend/app/review_policy.py`，由工作流的 `review_node` 调用。推演没通过时，原来“再单独检查外部资料，看能不能只靠资料给出判断”的流程也保留着。审查状态放宽，不代表最终一定会给概率。

## 改动效果
先在仓库根目录跑这个例子，不需要模型密钥：
```bash
uv run python eval/review_policy.py --case D03
```
它会把同一条“缺少发布计划”的意见交给新旧规则：旧版删掉并放宽状态，新版保留，仍然不通过。这就是最直接的前后区别。
想看全部固定案例，运行 `uv run python eval/review_policy.py`；想检查后端流程，运行 `uv run pytest -q`。
10 月 2 日的检查中，当前分支 63 项后端测试通过，16 个固定案例也都通过了。这组案例里有 10 条意见应该保留，旧版误删了 5 条，新版没有误删。
这些数字说明已知的处理错误修好了，还不能说明最终预测更准。测试用的是预先写好的审查意见，并没有让真实模型对一批问题重新预测。修好以后可能少漏掉问题，也可能更常要求补资料；最后的概率有没有更接近实际结果，还要另做比较。
案例由 AI 编写，人工复核待补。第一次测试中有一个此前没看过的案例没有通过，补规则后才通过，所以后来的 16/16 只能算已知案例复测。[首次失败](../eval/results/agent6-first-heldout.json)和[最终结果](../eval/results/agent6-policy-results.json)都保留着。
和 Agent 1–2 的 PR #1（`8fdd1b8`）临时合在一起后，139 项现有后端测试和 4 项补充流程测试通过。主分支没有改动。另一个受当天日期影响的旧测试也固定了时间，单独放在 `cb82d4b`，不计入上面的规则改进效果。
